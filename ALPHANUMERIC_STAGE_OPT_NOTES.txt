ALPHANUMERIC CUDA KERNEL - STAGED OPTIMIZATION NOTES (July 12, 2026)
================================================================================

Baseline before this pass (from tune_rtx5080_results.csv, RTX 5080, CUDA 13.3,
sm_120): 12.302 GH/s at --threads 512 --blocks-per-sm 4, kernel at 50 regs,
0 bytes local, 5120 bytes shared, batch 2^24.

This pass restructures the kernel and host path in the eight requested stages.
Every math change is verified in three independent ways WITHOUT a GPU (see
"Verification" below); the throughput numbers themselves must come from your
5080 - no performance numbers in this document are estimates or guesses, and
none are claimed.

--------------------------------------------------------------------------------
STAGE 1 - poll fix
--------------------------------------------------------------------------------
Old:  if(((poll++) & 255u) == 0u && ...)   -> the check fired on the FIRST
      iteration of every thread (poll==0), so every thread paid a global read
      of result->found before hashing anything.
New:  if(((++poll) & 255u) == 0u && (__ldcg(&result->found) != 0u ||
                                     __ldcg(live_gen) != job_gen))
      -> first global read after 255 hashes, then every 256.

The read also moved from a volatile pointer to __ldcg (L2-coherent load),
which is the correct primitive for polling a flag written by atomicCAS from
other blocks / by the host.

--------------------------------------------------------------------------------
STAGE 2 - reduction replacement (deficit accounting)
--------------------------------------------------------------------------------
Old:  every launch: 512-entry shared uint64 array, 9 __syncthreads passes,
      one atomicAdd per block to accumulate hashes_scanned.
New:  each thread's completed-iteration count has a closed form, so the kernel
      only accounts for the DIFFERENCE (deficit = expected - done):

        expected(tid) = tid < n ? (n - 1 - tid) / stride + 1 : 0
        done          = poll - (bailed ? 1 : 0)

      poll counts loop-body entries; the single entry that did not hash is a
      bail-break (found-break hashes first, so bailed stays false there). The
      deficit is warp-reduced with __shfl_down_sync, then one 16-word shared
      array + ONE __syncthreads combines warps, and the block adds to
      result->deficit ONLY when it is nonzero. On the common full-scan path
      that atomic never fires and the whole epilogue is a few shuffles.

      The host then reports hashes_scanned = enqueued - deficit. This is exact
      for every mix of full scans, found-breaks and cancel-bails (verified by
      the loop simulator, test 7), so the displayed hashrate stays honest.

Deliberate deviation from the task's literal suggestion: "if no share found,
thread 0 of block 0 writes nonce_count" is racy across blocks (a block can
observe found==0 while another block is mid-CAS) and silently over-reports.
The deficit scheme gives the same zero-cost common path with exact results in
all interleavings.

DeviceScanResult was re-laid-out to {found, pad, deficit, nonce, hash[32]} so
the per-launch clear is a single 16-byte cudaMemsetAsync (found+deficit only;
nonce/hash are gated by found and never read stale). Layout is locked with
static_asserts.

--------------------------------------------------------------------------------
STAGE 3 - 32-bit index arithmetic
--------------------------------------------------------------------------------
idx, stride and nonce_count are now uint32_t inside the kernel; the only
64-bit math per iteration is nonce = start_nonce + (uint64)idx. A single
launch is capped at SLICE_MAX = 2^31 nonces so idx + stride cannot wrap
(stride < 2^25 in practice). Larger requests are split host-side into
sequential slices on the same stream; between slices the host peeks the found
flag so a share stops further slices. Normal mining batches (<= 2^28) are
exactly one slice and pay nothing.

start_nonce stays uint64. Wrap past 2^64 is well-defined unsigned arithmetic
and produces distinct nonces (documented as safe rollover; the planner test
covers ranges that wrap).

--------------------------------------------------------------------------------
STAGE 4 - stream pipeline
--------------------------------------------------------------------------------
DevCtx now owns a nonblocking cudaStream_t. scan92 is: cudaMemsetAsync(16B) ->
kernel launch(es) -> cudaMemcpyAsync into a pinned host result -> ONE
cudaStreamSynchronize. cudaDeviceSynchronize is gone from the hot path, and
the result copy no longer implicitly serializes the whole device.

--------------------------------------------------------------------------------
STAGE 5 - configurable batch + honest latency reporting
--------------------------------------------------------------------------------
- Live mining: --batch-ms default changed 50 -> 15 (the auto-sizer already
  targeted wall-time; with in-kernel cancel there is no reason to run long
  batches for throughput, and 15 ms keeps share latency low).
- Benchmark: alphanumeric_cuda_benchmark_batch(dev, threads, bpsm, seconds,
  batch) returns {GH/s, avg_batch_ms, launches_per_sec, accounting_ok, ...}.
  avg_batch_ms is measured wall time per scan call (kernel + launch + sync
  overhead), not a derived guess. accounting_ok cross-checks stage 2 on the
  device: with the benchmark's impossible target every launch must report
  exactly `batch` completed hashes.
- CLI: --bench-batch-log2 N (default 24) picks the batch; --bench-sweep prints
  the 2^24..2^28 table. Old --benchmark output format is preserved with the
  extra fields appended.

--------------------------------------------------------------------------------
STAGE 6 - hash-path optimization
--------------------------------------------------------------------------------
Two changes, both in alphanumeric_blake3_core.cuh, both taking effect for
every nonce:

a) Per-job round-0 precompute. In compress-0 round 0 the four column G mixes
   consume m0..m7 and the diagonals consume (m8,m9) (m10,m11) (m12,m13)
   (m14,m15). The nonce lives only in m11/m12, so six of the eight G mixes are
   nonce-independent. The host applies them once per job
   (alpha_build_job_pre) and ships the partial state in the kernel parameter;
   the kernel finishes round 0 with just the two nonce-carrying diagonals.
   Saves 6 of 112 G mixes per hash.

b) First-word fast path with a split final round. The share test needs only
   the first big-endian word to reject virtually every nonce. h0 = v0 ^ v8;
   in the final round v0 is finalized by diagonal G(0,5,10,15) and v8 by
   diagonal G(2,7,8,13). alpha_hash92_head() therefore runs the final round's
   four columns plus only those two diagonals and returns h0 with the register
   state still live; the other two diagonals and the h1..h7 XORs
   (alpha_hash92_tail) run only for word-0 candidates and for full-hash
   callers. Saves 2 more G mixes plus 7 output XORs per rejected nonce.

   The tie path is unchanged in meaning: b0 < t0 accepts, b0 > t0 rejects,
   b0 == t0 completes the hash and runs the byte-lexicographic tail compare
   with equality valid - exactly the semantics the pool validated.

All message-schedule literals in the header were REGENERATED programmatically
from the official BLAKE3 permutation [2,6,3,10,7,0,4,13,1,11,12,5,9,14,15,8]
and diffed against the shipped kernel's 56 hand-written g() calls: identical.
The generated code is what compiles; the derivation removes transcription risk.

Nonce injection uses templated compile-time selectors (alpha_m0_sel<I>), so
slot 11/12 reads fold to the nl/nh registers and block-1 slots >= 7 fold to
literal zero - no runtime branching, no local-memory message array.

--------------------------------------------------------------------------------
JOB-CANCEL (stage-8-lite, implemented now because it is cheap and material)
--------------------------------------------------------------------------------
alphanumeric_cuda_request_cancel(): bumps an atomic job generation, writes it
to a pinned staging word and cudaMemcpyAsync's 4 bytes to the device on a
dedicated side stream. The kernel compares its launch-time generation against
the device word in the same 256-hash poll as the found flag and drains in
roughly the time of 255 hashes per thread. The runner calls it right after
both cancel.store(true) sites (mining.notify and mining.set_difficulty), so a
new job no longer waits for the old batch. Fire-and-forget by design: a lost
or late write only means the batch finishes normally and the existing job_seq
staleness check discards the result. Deficit accounting keeps the reported
hashrate exact for drained batches.

  - grep the scan kernel region for LDL/STL: there should be none (no local).
  - The h0 fast path shows as an early predicated branch after the first BSWAP
    (PRMT) + compare.

--------------------------------------------------------------------------------
STAGE 8 - persistent kernel: evaluated, deferred
--------------------------------------------------------------------------------
A persistent kernel (grid resident across jobs, work fed via mapped memory)
removes per-launch overhead. Measured need first: with batch 2^26 at the
baseline rate a launch is ~5.5 ms of work; launch+sync overhead is tens of
microseconds (avg_batch_ms in --bench-sweep now measures it directly as the
gap between wall time and pure kernel time across batch sizes). Unless the
sweep shows avg_batch_ms materially exceeding the kernel time at your chosen
batch, a persistent kernel buys < 1% and costs: watchdog/TDR interaction on a
display GPU, harder cancel semantics, a custom work queue, and much harder
correctness auditing. The generation-cancel already delivers the
responsiveness benefit. If the sweep does show meaningful per-launch overhead
at small batches, the prepared design is: one resident grid sized to
sm_count*bpsm blocks, a mapped-memory job slot {gen, AlphaJobPre, start,
count} the host rewrites, kernel loops on gen change, deficit accounting
unchanged per work item. Not implemented in this pass - measure first.
